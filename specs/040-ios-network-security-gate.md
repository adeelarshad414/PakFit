# iOS Network Security Gate

## Objective

Harden PakFit's internet-enabled iOS path by proving that runtime Swift code uses HTTPS-only search handoffs and that the current build does not add ATS cleartext opt-outs.

## Requirements

- iOS runtime Swift app/core source must not contain `http://` URL literals.
- iOS online calorie search must continue using an HTTPS search URL.
- iOS project/package/app/core metadata must not contain ATS cleartext opt-outs.
- CI and local release validation must run the same iOS network security gate.
- Release evidence must record the iOS runtime URL policy and network security gate status.
- Android and iOS version metadata must be bumped for release artifacts generated by this security-hardening slice.

## Boundaries

- This gate does not add a backend, API client, certificate pinning, or remote image processing.
- Future backend APIs, model endpoints, analytics, crash reporting, or remote image processing require a new transport security spec and privacy/security review.
- The gate intentionally scans Swift runtime source instead of plist DTD declarations, because `PrivacyInfo.xcprivacy` includes Apple's plist DTD URL and is not runtime traffic.
- This gate must not require signing secrets, App Store Connect access, backend services, analytics keys, or cloud health data.

## Acceptance Criteria

### Scenario: Runtime URL literals stay HTTPS-only

Given the release validation command runs
When iOS runtime Swift app/core sources are inspected
Then cleartext `http://` URL literals fail the gate
And the online calorie search remains HTTPS-based.

### Scenario: ATS cleartext opt-outs are blocked

Given the release validation command runs
When iOS project, package, and runtime Swift sources are inspected
Then ATS cleartext opt-outs fail the gate until a reviewed transport security spec exists.
